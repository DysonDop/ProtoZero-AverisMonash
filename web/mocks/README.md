# API fixtures

Hand-off mocks so the frontend can be built before the backend exists.

Every file matches a real endpoint in [`docs/contracts.md`](../../docs/contracts.md) §6,
shape for shape. When Gene's API is up, swap the fixture path for the real base
URL and nothing else in the frontend should change.

| Fixture | Endpoint it stands in for |
| --- | --- |
| `health.json` | `GET /api/health` |
| `cases.json` | `GET /api/cases` (`CaseSummary[]` + `next_cursor`) |
| `cases/email_XXX.json` | `GET /api/cases/{email_id}` (full `Case`) |
| `documents/email_XXX_SI.json` | `GET /api/cases/{email_id}/document/SI` |
| `documents/email_XXX_BL.json` | `GET /api/cases/{email_id}/document/BL` |
| `review.json` | `GET /api/review` |
| `metrics.json` | `GET /api/metrics` |

## The values are real, not invented

Generated by reading the actual dataset. Every `value`, `evidence` and
`label_seen` is copied from the source document, and every `Locator` carries
**real character offsets** verified to slice back to exactly the stated value
(40 of 40 correct at time of writing).

So this works, and is the whole point of screen two:

```js
const text = doc.text                       // from documents/email_004_BL.json
const f    = comparison.bl                  // the BL side of one row
text.slice(f.locator.char_start, f.locator.char_end)   // === f.value
```

`locator.line` is a 0-indexed line number into the same text, if you would
rather scroll to a line than to an offset.

## Two things to know before you build

**1. Highlighting is three render paths, not one.** Every fixture here is a
`.txt` document, so they all use `char_start`/`char_end`. The real dataset also
has PDFs (28 files), spreadsheets (22) and Word documents (8). Per
`contracts.md` §2, those populate the `Locator` differently:

| Format | What you get | How you highlight |
| --- | --- | --- |
| `txt`, `docx` | `line`, `char_start`, `char_end` | offsets into `text` |
| `pdf`, `scan_pdf` | `page`, `bbox` | overlay a box on the page image from `page_urls` |
| `xlsx` | `sheet`, `line` | highlight a row in a rendered table |

Build the text path first, but do not assume one component covers all three.

**2. Render `status` and `defect_fields` as given.** The backend asserts the
invariants in `contracts.md` §4 (for example `has_defect` is true **iff**
`status == "MISMATCH"`, and `NEEDS_REVIEW` always has empty `defect_fields`).
Do not recompute them in the UI. If they ever look wrong, that is a backend bug
to report, not a frontend workaround.

## Honesty note on the escalation labels

The five `NEEDS_REVIEW` reasons were **derived from the documents** (wrong
document type detected by content, unreadable detected by an empty or
undecodable file, missing values detected by blank fields), then checked against
the organisers' key. Four of five agreed on the first correct run.

The one exception is `email_506`. A comparison request with **zero**
attachments is genuinely indistinguishable from the 91 legitimate "please send
me the draft BL" emails using the email alone (see
`docs/dataset_facts.md` §8). Its label was taken from the key **for this fixture
only**, so the review screen has a no-attachment card to render.

**This folder is mock data for UI development. It is not eval data, and nothing
here should be used as expected output for the pipeline.**
